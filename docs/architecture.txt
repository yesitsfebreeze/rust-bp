# Runtime architecture

Documentation index: [llms.txt](../llms.txt).

The registered runtime executable owns MCP and supervision in one process:

    agent --stdio/JSON-RPC--> daemon mcp
                              |-- supervisor + daemon.sock
                              |-- rust-analyzer (started on demand)
                              |-- app + app.sock (live channels/state)
                              |-- bounded profiling commands

MCP requests are handled directly in src/runtime/daemon/mcp/mod.rs. There is no
per-request worker. Initialize, tools/list and status {start:false} do not start
the app. reload, status, channels and lsp start the supervisor when needed.
The supervisor watches src/ and Cargo.toml, builds the app/modules and swaps
only successful generations. Its socket prevents two supervisors per project.
MCP owns the supervisor thread, socket workers and language server. stop closes
them and the app; MCP remains ready for a new reload. EOF closes owned resources.
A client attaching to an existing supervisor does not own its lifetime.

The standalone serve and --call commands use the same runtime executable.
A one-shot CLI call can start a detached supervisor with a 30-minute idle limit;
persistent MCP uses its own in-process supervisor. Output from the supervised
app goes to daemon.log so it cannot corrupt JSON-RPC stdout. Runtime executable
changes require rebuilding and reconnecting; app and module changes reload
through the supervisor. On Windows, disconnect before rebuilding the runtime.

The starter calls daemon::channels::serve once, ticks a stateful module and
answers checkpoint requests. Module-only edits keep the app process; app edits
checkpoint app/module state before restarting. See [reload](reload.txt).
Channels record counters, timing histograms and last values in the app process.

One rust-analyzer index is reused until the supervisor stops. The LSP bridge
returns 1-based source coordinates; edit previews retain LSP UTF-16 ranges.
AST queries use ast-grep from the project root. Native memory inspection reads
the live app; Valgrind runs separate bounded workloads, natively or in Docker.

Builds and tool calls record to events.jsonl in the project runtime directory.
MCP emits standard logging notifications for build failures. The optional
rustc-events compiler wrapper records individual crates, including terminal
builds. No client-specific hooks, queue adapters or session configuration exist.

## Build profiles

Defined in the root `Cargo.toml`; the choice follows what each build is for.

| profile        | used by                         | debug info                                   | why                                                                   |
|----------------|---------------------------------|----------------------------------------------|-----------------------------------------------------------------------|
| `dev`          | `cargo test`, `cargo check`     | line tables for workspace crates, none for deps | fast inner loop, readable backtraces                                 |
| `release`      | daemon swaps, valgrind, `leaks` | line tables for workspace crates, none for deps | callgrind annotation and leak callstacks need file:line, nothing more |
| `distribution` | `cargo build --profile distribution` | none; `strip`, `lto`, `codegen-units = 1`  | the small binary to ship; nothing in the framework uses it            |

`release` deliberately has no `strip`, `lto` or `panic = "abort"`: they remove
the symbols the profilers report against and change the unwinding and heap
paths being measured. Put size work into `distribution`.
